# RAISE Workflows and Use Cases

## 1. Verified website-production workflow

**Completed and used in this project:**

```text
Define the need
→ inventory evidence and source files
→ draft traceable content
→ build a bounded feature
→ run automated checks
→ inspect the change and browser behaviour
→ record open items
→ request professor approval
```

The workflow deliberately separates evidence, implementation, automated validation, human review, and approval. Automated checks reduce avoidable mistakes but do not replace academic or organisational judgement.

## 2. Teaching workflow represented by RAISE Hub

**Used as the organising model for workshop content:**

1. **Decide/Define** — identify the task, intended user, constraints, and what should not be handed to AI.
2. **Build** — create a small, specific assistant or artefact using controlled source material.
3. **Test** — use realistic examples and look for factual, instructional, accessibility, bias, and privacy problems.
4. **Reflect** — document limitations, uncertainty, and the division of responsibility between the tool and the user.
5. **Improve** — revise the tool or workflow and return the final decision to the responsible faculty member.

For teaching assistants, the final step is a **faculty hand-back**: present what was built, the evidence from testing, limitations, and a recommendation. The faculty member retains the release decision.

## 3. Workshop-to-web workflow

**Completed and demonstrated:**

```text
Workshop deck or participant material
→ evidence/content inventory
→ concise web summary
→ linked workshop/project/resource records
→ authentic image selection and provenance
→ draft review page
→ automated and browser checks
→ approval gate
```

This process avoids writing promotional claims that are not supported by the workshop materials. It also preserves the distinction between a workshop demonstration and a deployed product.

## 5. Proposed teaching and operational use cases

The following ideas were identified but were **not fully implemented or evaluated** during this internship.

### Evaluation-record assistant — proposed / not yet tested

Help a reviewer structure evidence under accuracy, bias/fairness, limits/uncertainty, power/public value, and responsible-use decision. It should never generate a passing evaluation from the tool’s own claims; a named human reviewer must approve the record.

### Workshop-to-web publishing pipeline — partially implemented

Extend the current content inventory and validation approach so a reviewed workshop record can produce a web entry, related-resource links, image requirements, and a release checklist. Approval must remain manual.

### “Decide what to hand AI” interactive guide — proposed / not yet tested

Guide students, teaching assistants, or faculty through task decomposition, privacy, evidence requirements, acceptable assistance, and responsibility. The output should be a decision aid, not institutional policy.

### Peer-organisation scan — proposed / not yet tested

Compare how university AI-support hubs describe services, governance, training, evaluation, and access. Sources, dates, and institutional differences must be recorded; current web claims should not be treated as proof of impact.

### Teaching-support workflow — proposed / not yet tested

Support syllabus/Canvas-page drafting, example generation, accessibility review, and question design while requiring source verification and faculty hand-back before learner release.

## 6. Proposed research-support workflow

**Proposed / not yet tested as a complete research workflow:**

1. Define the research question and what evidence is admissible.
2. Build a source inventory with stable citations and access dates.
3. Use AI for bounded tasks such as query expansion, classification suggestions, or draft code explanations.
4. Keep a prompt/model/date/test log and preserve reproducible inputs where privacy allows.
5. Verify quotations, citations, calculations, and interpretations against primary sources.
6. Record exclusions, uncertainty, bias risks, and researcher decisions.
7. Obtain ethics/data approval before using personal, participant, or restricted information.

Potential applications include literature/evidence mapping, qualitative coding support, survey-instrument review, reproducibility documentation, and research communication. None should be described as a validated RAISE service until it has been piloted and evaluated.
